AUDITORIA FULLPOS - AUTORREPARACION, BACKUPS, BUSINESS_ID Y LICENCIA LOCAL
Fecha: 2026-06-17
Modo de auditoria: solo lectura del proyecto. No se modifico codigo, no se abrio ni se migro la base de datos, no se genero business_id y no se cambio la logica de licencias.

================================================================================
RESUMEN EJECUTIVO
================================================================================

FullPOS tiene una estrategia real de autorreparacion para SQLite:
- al iniciar la app abre la base de datos;
- si falla por corrupcion, intenta restaurar el ultimo backup ZIP;
- si no hay backup valido, pone la base actual en cuarentena y crea una base nueva;
- despues del open ejecuta AutoRepair, borra WAL/SHM, corre PRAGMA quick_check/integrity_check y restaura backup si falla;
- DbHardening valida tablas/columnas criticas y reintenta operaciones ante locks o DB cerrada;
- DatabaseRecoveryService limpia tickets POS abandonados.

El sistema de autorreparacion protege principalmente la base SQLite principal y la carpeta Documents/product_images cuando se usan backups ZIP completos.

No protege de forma directa:
- business_id;
- license.lastInfo;
- license.licenseKey;
- license.deviceId;
- licencia local %APPDATA%/FullPOS/license.dat;
- cola pending_registration_queue_v1.json;
- archivo JSON de SharedPreferences.

El business_id vive en SharedPreferences, clave business.business_id_v1. La licencia cacheada vive tambien en SharedPreferences. El token local vive en %APPDATA%/FullPOS/license.dat. Los backups ZIP no incluyen estos archivos. Por eso, despues de un apagon, la base puede restaurarse y la app puede volver a abrir, pero la identidad/licencia local puede quedar perdida o inconsistente si se corrompio SharedPreferences o license.dat.

ARCHIVO:
lib/core/bootstrap/app_bootstrap_controller.dart
METODO / CLASE:

LINEA APROXIMADA:
100-175
QUE HACE:
Controla el arranque. Carga configuracion, abre AppDb.database, si falla intenta AutoRepair.ensureDbHealthy(reason: 'bootstrap_open_failed'), vuelve a abrir, ejecuta AutoRepair.ensureDbHealthy(reason: 'bootstrap'), luego DbHardening.preflight() y DatabaseRecoveryService.run().
CUANDO SE EJECUTA:

QUE DATOS PROTEGE:
Indirectamente protege datos dentro de SQLite: productos, ventas, clientes, caja, turnos, cotizaciones, compras, usuarios, configuracion de negocio dentro de tablas, etc., siempre que exista backup/restauracion o reparacion de esquema.
QUE DATOS NO PROTEGE:
business_id en SharedPreferences, licencia cacheada en SharedPreferences, license.dat, pending_registration_queue_v1.json, token/estado offline de licencia.
RIESGO:
La app puede declararse lista despues de reparar/recrear SQLite, pero sin haber restaurado identidad/licencia local.
RECOMENDACION:
Agregar una fase explicita de health-check de identidad/licencia antes/despues de la reparacion DB: verificar business_id, license.lastInfo, device_id y license.dat, sin generar valores nuevos automaticamente.

================================================================================
RESPUESTAS DIRECTAS A PREGUNTAS CLAVE
================================================================================

1. Que mecanismo de recuperacion existe actualmente:
   - Restauracion automatica de SQLite desde ZIP.
   - Cuarentena y recreacion de DB si no hay backup.
   - Limpieza WAL/SHM.
   - PRAGMA quick_check/integrity_check.
   - Reparacion de esquema con CREATE TABLE/ALTER.
   - Backup pre-migracion.
   - Backups automaticos por ciclo de vida.
   - Limpieza de POS tickets abandonados.
   - Reparacion de SharedPreferences solo por renombrado del JSON corrupto, sin recuperar valores.
   - Cuarentena manual de license.dat invalido.

2. Fallos detectados:
   - DB corrupta/malformed/not a database.
   - WAL/SHM potencialmente danado por eliminacion.
   - DB locked/busy por reintentos.
   - DB cerrada por reopen.
   - Tablas/columnas faltantes parciales.
   - integrity_check fallido.
   - Migracion fallida mediante backup pre-migracion.
   - Archivo DB faltante se trata como primera creacion.
   - SharedPreferences corrupto solo si se usa PrefsSafe.
   - license.dat invalido en flujo de licencia.

3. Fallos no cubiertos completamente:
   - Journal rollback .db-journal no se limpia/copia explicitamente.
   - SharedPreferences no se respalda/restaura.
   - license.dat no entra al backup.
   - pending_registration_queue no entra al backup.
   - Verificacion de backup puede ser best-effort y aceptar null.

4. Carpetas/archivos usados:
   - DB principal: Documents/fullpos.db, fullpos.db-wal, fullpos.db-shm; fallback Application Support/fullpos.db.
   - ZIP backups: Documents/FULLPOS_BACKUPS/backup_TIMESTAMP_TRIGGER.zip.
   - Cuarentena DB: Documents/FULLPOS_BACKUPS/quarantine/db_TIMESTAMP/.
   - Pre-migration: Documents/FULLPOS_BACKUPS/pre_migration/backup_before_migration_*.
   - AutoRepair raw backup: Documents/FULLPOS_BACKUPS/auto_repair_before_*.
   - DbBackup rapido: Application Support/backups/fullpos_db_*.sqlite.
   - Logs AutoRepair: Documents/FULLPOS_LOGS/auto_repair.log.
   - Logs DbHardening: Application Support/logs/db_hardening.log.
   - business_id/licencia cache: Application Support shared_preferences JSON.
   - token local licencia Windows: %APPDATA%/FullPOS/license.dat.

5. Cada cuanto crea backups:
   - Automatico al pasar a paused/inactive tras 12 segundos si enable_auto_backup=true.
   - Automatico inmediato en detached.
   - Anti-spam minimo 30 segundos entre auto backups.
   - Manual desde pantallas de backup/settings.
   - No se encontro scheduler periodico por hora/dia.

6. Retencion:
   - ZIP: default 15, configurable 1..60 con backup_retention_count.
   - DbBackup interno: maximo 10 .sqlite.
   - Pre-migration/quarantine/auto_repair raw no tienen retencion clara en los archivos auditados.

7. Datos protegidos por backup ZIP:
   - Todo lo que vive dentro de SQLite: productos, ventas, clientes, compras, caja, turnos, cotizaciones, usuarios, configuracion de negocio en tablas, facturacion electronica, backup_history, etc.
   - Documents/product_images si existe.

8. Datos criticos no protegidos:
   - business_id.
   - license.lastInfo / license.licenseKey / license.deviceId.
   - license.dat.
   - datos de activacion fuera de DB.
   - pending_registration_queue_v1.json.
   - terminal_id/session prefs.

9. Dependencias inestables:
   - No encontre que business_id dependa de MAC, nombre PC, usuario Windows, MachineGuid, disco, volumen o BIOS UUID.
   - device_id/terminal_id local se genera aleatorio en SharedPreferences; no es hardware, pero es inestable si prefs se pierden.

================================================================================
CONCLUSION FINAL
================================================================================

1. La autorreparacion actual NO protege el business_id. Lo puede conservar solo si SharedPreferences sobrevive o si license.lastInfo tambien sobrevive y el guardia lo restaura.

2. La autorreparacion actual NO protege completamente la licencia local. El backup SQLite no incluye license.dat ni license.* de SharedPreferences.

3. Si hay un apagon, si solo se corrompe SQLite y hay backup sano, el business_id no deberia cambiar porque esta fuera de SQLite. Pero si el apagon corrompe SharedPreferences o license.dat, si puede perderse el business_id/licencia local. El codigo actual no genera business_id nuevo automaticamente en BusinessIdentityStorage, pero puede caer a flujos de restauracion/cache o legacy device_id.

4. Si existe riesgo de que la app regenere un "negocio local" en sentido operativo: si la DB se pone en cuarentena y no se restaura backup, AppDb crea DB nueva, crea tablas, inserta catalogo demo y business_settings default FULLPOS. Eso no genera business_id licenciado por si solo, pero si crea una instalacion operativa vacia/default.

5. Lo primero a revisar/corregir:
   - Crear un "identity recovery bundle" atomico y redundante para business_id + license.lastInfo + license.dat metadata + terminal_id.
   - Incluirlo en backup/restore o crear backup separado firmado.
   - Cambiar PrefsSafe para no convertir corrupcion de SharedPreferences en perdida silenciosa de business_id/licencia.
   - Endurecer AppDb/BackupService para exigir integridad true al restaurar y para no recrear DB nueva sin alertar cuando hubo corrupcion.
